# STM32 Project Refactoring Guide

This document outlines the recommended approach to refactoring an STM32 project generated by STM32CubeMX/CubeIDE (specifically addressing the large `main.c` file). 

The primary goals of this refactoring are to:
1. **Respect CubeMX Code Generation:** Ensure that future hardware configuration changes in CubeMX do not overwrite or delete custom application code.
2. **Improve Maintainability:** Divide the monolithic `main.c` into manageable, modular files.
3. **Future-Proof the Architecture:** Make it easy to add new features, subsystems, or tasks without continuously bloating a single file.

---

## 1. The Golden Rule: Minimal `main.c`

In an STM32Cube environment, `main.c` should be treated as a **bootloader for your RTOS and hardware**. It should do as little application-level work as possible. 

`main.c` should strictly be responsible for:
- Auto-generated hardware initialization (e.g., `HAL_Init()`, `SystemClock_Config()`, `MX_GPIO_Init()`).
- Auto-generated FreeRTOS object creation (mutexes, semaphores, queues, threads).
- Starting the scheduler (`osKernelStart()`).

All custom includes, variables, and function calls placed in `main.c` **must** reside strictly within the `/* USER CODE BEGIN ... */` and `/* USER CODE END ... */` block tags.

## 2. Proposed Architecture (Separation of Concerns)

To avoid a massive `main.c`, the application should be split into **Tasks** and **Subsystems**.

### A. FreeRTOS Tasks (`Core/Src/tasks/`)
Each major FreeRTOS task should have its own `.c` and `.h` file.
- `task_main.c` / `.h`: The central application state machine (currently `mainTask`).
- `task_sensors.c` / `.h`: The sensor querying logic (`sensorQueryTask`).
- `task_comms.c` / `.h`: The radio/payload communication logic (`uartRxTask` / downlink / beacon).
- `task_usb.c` / `.h`: The USB handling logic (`usbTask`).

### B. Subsystems & Drivers (`Core/Src/subsystems/` or `Core/Src/drivers/`)
Hardware-specific and feature-specific logic should be abstracted away from the tasks into standalone modules.
- `sys_storage.c` / `.h`: Abstraction for LittleFS and FatFS operations (mounting, reading boot count, file downlink).
- `sys_eps.c` / `.h`: EPS protocol handling, parsing, and formatting (`EPS_Perform_Transaction`).
- `sys_payload.c` / `.h`: KISS encoding/decoding and payload logic.

## 3. Step-by-Step Refactoring Process

Follow these steps to safely refactor the code without breaking CubeMX compatibility:

### Step 1: Create the new files
Create your new `.c` and `.h` files in `Core/Src` and `Core/Inc` (or inside custom folders like `Core/Src/tasks`). If you use custom folders, ensure you add them to the compiler's include paths in the CubeIDE project settings.

### Step 2: Extract Task Bodies
1. Go into `main.c` and locate the task definitions (e.g., `void mainTask(void *argument) { ... }`).
2. Cut the entire body of the task.
3. Paste the body into your new `task_main.c` file. 
4. Include any necessary headers (like `main.h`, `cmsis_os.h`, and your custom headers) in `task_main.c`.
5. Ensure the task function signature matches exactly what CubeMX generated.

### Step 3: Link it back to `main.c`
1. Open `main.c`.
2. Find the `/* USER CODE BEGIN Includes */` block at the top.
3. Add `#include "task_main.h"` (and the headers for any other tasks you extracted).
4. CubeMX will continue to auto-generate the `osThreadNew` calls in `main.c` and the weak/empty prototypes, but the actual execution will jump to your separate `.c` files.

### Step 4: Extract Subsystems
Extract local helper functions (like `EPS_Perform_Transaction`) and massive variable declarations (like `eps_sensors_data` mapping) out of the tasks and into your new Subsystem files (`sys_eps.c`). Expose clean, simple API functions in the subsystem headers (e.g., `EPS_Init()`, `EPS_ProcessData()`).

## 4. Why this approach?

- **Safe Generation:** If you add a new UART in CubeMX and regenerate the code, CubeMX only touches `main.c` and the HAL files. Your `task_*.c` and `sys_*.c` files are completely ignored by the code generator and remain safe.
- **Merge Conflicts:** If multiple people work on the project, one person can work on `task_comms.c` while another works on `sys_storage.c` without causing massive git merge conflicts in `main.c`.
- **Testing:** Separated modules can be unit tested individually off-target.
